N. The lifecycle of an API request behind a CDN

DNS basics API request lifecycle Caching strategies Load balancing

What you'll learn: how a user's HTTPS request travels from their browser through DNS → CDN edge → origin load balancer → API server → database, and how to think about latency and failure at each hop. After this you'll be able to read a trace and pinpoint the slow component.

When you type api.example.com/users/42 in your browser, a chain of network components work in sequence: DNS resolves the name to an IP, the CDN may answer from cache or proxy to the origin, the load balancer routes to one of many API servers, and finally the API server queries the database and renders a response.

The total latency budget is usually under 200 milliseconds for an interactive feel. Each component consumes part of that budget. If something feels slow, the answer is almost always "one specific hop is slower than it should be" — never "the network is generally slow."

The architecture matters for failure as much as for latency. If the CDN drops a cache hit rate from 95% to 30%, you don't notice "things are a bit slower" — you notice the origin burning under 3× its usual load and timeouts spreading.

Each component's role.

  1. Browser. Initiates the request. Includes TLS handshake on the first connection (~50ms additional once per session via TLS resumption).
  2. CDN edge. Geographically close to the user (typically <30ms RTT). Holds cached responses keyed by URL + query params. Cache hit serves directly; cache miss proxies to origin.
  3. Load balancer. Distributes traffic across many API replicas. Uses round-robin, least-connections, or hash-based routing. Performs health checks; routes around dead instances.
  4. API server. Application logic. Parses request, authenticates, queries the database, formats response. The slowest hop usually (~5-50ms depending on complexity).
  5. Database. Holds the source of truth. Read-replicas serve queries; primary handles writes. Index lookups are O(log N); full scans are O(N) and a common slowness culprit.

The data flow as pseudocode:

request_lifecycle.py pseudocode 
def serve_request(url):
    cached = cdn.lookup(url)                      # 1: CDN cache lookup
    if cached and not cached.expired:             # 2: cache hit path
        return cached.body                        #    short-circuit (~50ms total)
    target_server = lb.pick_healthy_replica()     # 3: load balancer picks
    response = target_server.handle(url)          # 4: API server processes
    cdn.store(url, response, ttl=300)             # 5: write-through cache
    return response                               #    cache-miss path (~140ms)

In plain words: if the CDN has a fresh copy, return it immediately. Otherwise, hand off to a healthy backend, get the response, populate the CDN cache, and return the result.

Total: 144 ms. User perceives this as snappy (under the 200ms target). The biggest cost is the trans-Atlantic hop (hop 4 + hop 9 = 110 ms combined). If the CDN had a cache hit at hop 3, the request would have completed at hop 2 + edge round-trip ≈ 50 ms total.

If the cache hit rate drops to 30% instead of 95%, the AVERAGE latency goes from 0.95·50 + 0.05·144 = 54.7 ms to 0.30·50 + 0.70·144 = 115.8 ms — more than 2× slower for the SAME user behavior. This is why CDN cache hit rate is the metric to watch.

Takeaway. The 5-hop architecture has one fundamental property: the CDN hides the rest of the stack when its cache hit rate is high. Everything downstream of the CDN edge — the origin LB, the API servers, the database — is BUFFERED by the cache. A 95% cache hit rate means the origin only sees 5% of traffic. Lose the cache, and the origin must handle 20× load it was provisioned for.

⚠ Failure modes worth memorizing

  • CDN cache stampede. A popular item's TTL expires; thousands of edges miss simultaneously; origin gets a sudden 1000× spike. Mitigation: stagger TTLs, use stale-while-revalidate.
  • Database connection saturation. API server's connection pool fills; new requests queue; queue overflows; 503s start. Symptom: latency cliff, not gradual degradation.
  • Slow query → connection pool exhaustion. One 5-second query holds a connection. Pool drains. Now ALL requests are slow. Symptom: cascading failure.
  • Cross-region latency tax. Trans-Atlantic adds 80-100ms RTT. If your CDN misses, you can't beat this without geo-distributed origin.

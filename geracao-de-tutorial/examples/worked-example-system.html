Worked example: tracing a Stripe webhook through our queue → worker → database pipeline

Setup. Stripe sends POST /webhooks/payment_succeeded with a 2KB JSON payload. Our system: webhook endpoint receives, drops onto SQS, worker pulls and processes (updates DB, sends notification, returns).

Per-hop trace with latency and cumulative cost
Hop Component Action Bytes Latency Cumulative
1 Stripe → ALB TLS handshake (cached cert), POST body received 2,048 45 ms 45 ms
2 ALB → webhook svc Route by path, forward to one of 3 replicas 2,048 3 ms 48 ms
3 Webhook svc Verify Stripe-Signature HMAC; parse JSON 2,048 5 ms 53 ms
4 Webhook svc → SQS SendMessage with payload + dedup key 2,128 12 ms 65 ms
5 Webhook svc → Stripe Return 200 OK to acknowledge receipt 0 2 ms 67 ms (Stripe waits this long)
6 Worker SQS long-poll picks up message (avg 100ms delay) 2,128 100 ms 167 ms
7 Worker → DB UPDATE invoice SET paid=true (indexed lookup) ~200 8 ms 175 ms
8 Worker → SES Queue email notification ~3,000 30 ms 205 ms
9 Worker → SQS DeleteMessage (acknowledged) ~100 6 ms 211 ms

Total: 211 ms end-to-end. Stripe's perspective sees 67 ms (we ack immediately after enqueueing). Customer's invoice is marked paid by 175 ms; notification email is queued by 205 ms.

Scenario variation — what if SQS is slow? If SQS receive latency spikes to 2 seconds (instead of 100 ms), the user-visible "paid" status updates 2 seconds later — but Stripe still sees a 67ms ack, so they don't retry the webhook. Decoupling the ack from the work (steps 4-5 vs 6-9) is what makes this resilient.

Scenario variation — what if the DB is down at hop 7? Worker fails to ack the SQS message (no DeleteMessage). After SQS visibility timeout (30s default), another worker re-pulls. After 5 failed attempts, message goes to dead-letter queue. Total user-visible delay: depends on how long the DB stays down + visibility timeout.

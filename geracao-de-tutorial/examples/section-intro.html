1. Introduction

By the end of this tutorial, you will be able to apply a 4-stage performance recipe that takes a slow, load-shedding JSON API and turns it into one that holds a p99 under 200 ms while sustaining 5,000 req/s — without rewriting it in a faster language. You'll know what each stage does, why we tuned its parameters the way we did, what the bear traps are, and how to verify your service matches expectations after each stage.

Audience and prerequisites

This tutorial assumes you know:

  • HTTP service basics — request/response, status codes, JSON APIs.
  • A relational database at the level of "what an index is and why a query can be slow."
  • Basic load testing / the shell — running a load generator, reading latency percentiles.

This tutorial does not assume:

  • Familiarity with cache stampede protection, CDNs, or connection pools (we'll cover them).
  • Knowledge of any specific cache or CDN product — the recipe is vendor-neutral.
  • Distributed-systems theory (we stay concrete and measured).

How the tutorial is organized

The recipe is a 4-stage pipeline (one of which is skipped — we'll explain why):

Stage 0: Profiled baseline Stage 1: Caching layer Stage 2: Rust rewrite (skipped) Stage 3: DB indexing Stage 4: CDN + pool tuning

The tutorial walks each stage in order, with the same structure for each:

  1. Intuition — plain English: what this stage does and why.
  2. Geometry — a diagram or animated SVG showing the mechanism visually.
  3. Config or pseudocode — the concrete parameters and logic.
  4. Worked example — real numbers from an actual run.
  5. Takeaway — what to remember, and what's coming next.

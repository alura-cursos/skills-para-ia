Appendix

A. Bear traps (the 12 things that ate hours)

If you only read one appendix subsection, make it this one. Each entry includes the symptom, the root cause, and the fix.

A.1 Cache stampede at TTL expiry

Symptom. Every ~300 s, p99 spikes to ~900 ms for a few seconds — a latency sawtooth synced to the cache TTL.

Cause. When a hot key expires, all concurrent requests miss simultaneously and hit the database together → DB CPU pegs → the request queue backs up.

Fix. Turn on single-flight (one request recomputes; the rest await it) plus stale-while-revalidate. See §6.

A.2 Silent cache bypass — key collision

Symptom. hit_rate=0, origin QPS jumps to 100% of a namespace's traffic, p99 climbs — with no error logged.

Cause. A query-normalization change made the same request compute a NEW cache key every time; every lookup missed. Every key unique; hit rate 0 everywhere.

Fix. Pin key derivation to a versioned cacheKey(normalize(input)) and bump the namespace suffix (:v4) on any change. See §6.4.

A.3 Connection-pool exhaustion deadlock

Symptom. Under load, latency climbs, then requests hang and time out in waves — while DB CPU is idle (it's waiting, not working).

Cause. The pool is smaller than the number of concurrent slow queries; new requests block on a connection that never frees. With no acquire timeout, the wait is unbounded.

Fix. Set a pool acquire timeout (fail fast, shed load) + size the pool to ~(cores × 2) and give read replicas a separate pool. See §9.2.

B. Glossary

Cache hit rate
Fraction of reads served from cache without touching the origin. Formula: hits / (hits + misses). See §6.
p50 / p99
Median and 99th-percentile latency. p99 is the "tail" a fraction of users feel; it dominates perceived slowness under load. See §3.
Single-flight
Request coalescing: when several requests miss the same key at once, ONE recomputes the value and the rest await its result instead of all hitting the origin. See §6.2.
Stampede (thundering herd)
Many concurrent requests missing the same just-expired key and hitting the origin together, spiking load. The problem single-flight solves. See §6.2.
SLO
Service Level Objective — the target you hold yourself to. Here: "99% of requests complete under 200 ms at peak." See §3.
Stale-while-revalidate
Serve the expired cached value immediately while refreshing it asynchronously, so no request waits on the recompute. Trades a little staleness for zero refresh stalls. See §6.2.
Connection pool
A fixed set of reusable database connections shared across requests. Too few → queueing; too many → the DB itself is overloaded. See §9.2.
N+1 query
Fetching a list, then issuing one query per item instead of a single batched query. A classic hidden latency source on the miss path. See §8.2.
Negative caching
Caching "not found" (404) responses briefly so repeated requests for a missing key don't keep hitting the origin. See §6.6.
CDN
Content Delivery Network — edge servers that cache cacheable responses close to users, offloading the origin. Refines resilience but can't replace an origin cache. See §9.

E. Limitations and open questions

Honest accounting of what this recipe does not address:

  • Scale. Validated at 5,000 req/s peak. Behavior at 50k+ (multiple origin shards, cross-shard cache coherence) is untested.
  • Read-heavy assumption. The recipe targets read-heavy APIs. Write-heavy workloads need different tactics (write-through, CQRS, event sourcing) — caching alone won't help.
  • Single region. No data on multi-region cache coherence or geo-routing; the CDN section assumes one origin region.
  • Consistency. The 300 s catalog TTL means up to 5 minutes of staleness on non-inventory fields. Not suitable where reads must be strongly consistent.
  • Runtime. Measured on a Go service; GC-heavy or single-threaded runtimes may shift the p50/p99 numbers materially. Re-measure on your stack.
